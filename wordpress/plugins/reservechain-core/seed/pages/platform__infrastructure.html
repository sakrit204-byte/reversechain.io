Architecture at a glance

Evidence at the bottom, ledger at the top

The architecture is layered so that no layer can assert more than the layer beneath it supports. The ledger reads reserves from attestations. Attestations read from the registry. The registry reads from approved evidence. Nothing flows back down without review.

Functional components

Eleven components, one data model

Each component has one job and one owner role. The components share a single data model, so a figure shown in one place cannot disagree with the same figure shown elsewhere.

Industrial Metals Registry

Typed records for programs, lots, batches, containers, coils, laboratories, certificates, custody, valuations, insurance, reserve reports, token programs, redemptions and documents. The fields are declared once in a schema, and that schema drives the editor, the API and the passport.

Digital Asset Passports

Built on request from approved records. Each passport carries its stage-by-stage lifecycle, linked documents with fingerprints, parent and child units, and a Merkle root over all of it.

[rc_status s="in_development"]

Verification records

Laboratory, certificate and sampling records are linked to the unit they describe. Each certificate holds a source field that distinguishes owner-supplied evidence from independently commissioned evidence.

[rc_status s="in_development"]

Custody records

Receipts, seal numbers, locations and inspection events are linked to containers and bobbins. The data model is ready, but no custodian has been appointed to populate it.

Compliance controls

KYC/KYB status, jurisdiction lists, eligibility decisions and restrictions. Off-chain decisions are mirrored to the on-chain ComplianceRegistry by a separately permissioned operator.

[rc_status s="in_development"]

Tokenization engine

Token-program records hold every economic parameter, and all of them are unset by default. The contracts enforce reserve-gated minting, transfer screening, pause and role separation.

[rc_status s="in_development" label="Testnet only"]

Reserve and reconciliation engine

Computes declared and verified quantities by program, metal and unit from approved data. Reserve attestations are posted to ReserveGuard with a report hash and an as-of date.

[rc_status s="in_development"]

APIs

A versioned REST namespace, rc/v1, provides public read endpoints for programs, passports, documents, verification and registry statistics, and authenticated endpoints for participants.

[rc_status s="in_development"]

Participant access

Portal and mobile sign-in with MFA, holdings, notifications and redemption requests. The functions that move value stay locked until written authorization activates them.

Reporting

Reserve reports, registry exports, audit-trail verification and passport JSON exports. Every report is reproducible from the same approved data.

Data flow

How a fact reaches the public

A certificate value travels the same path as every other fact. If it skips a step it is not published.

  1. Captured

    A registry manager enters the record and uploads the source document. The platform computes the file's SHA-256 fingerprint on upload.

  2. Submitted

    The record enters "Under Review". Draft and under-review content is never public, never indexed and never returned by the API.

  3. Approved

    A different user approves it. The approval is bound to a fingerprint of the content and registry fields at that moment.

  4. Published

    Before publishing, the platform re-checks the fingerprint. If anything changed after approval, the record goes back to review.

  5. Served

    The website, passport, Proof-of-Reserves dashboard and apps read the published record through rc/v1.

Operating modes

Capabilities switched on by authorization, not by deployment

Designed to extend

New asset classes are new schemas, not new platforms

Record types and their fields are declared, not hard-coded. A future category such as precious metals would add a schema and a program record. The workflow, passports, audit trail and contracts stay the same. Future categories remain pre-launch until approved.
