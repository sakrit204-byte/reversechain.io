Our position

Controls you can inspect, not badges you must trust

The platform is in development. Some of the controls below are implemented in code today. Others are designed and scheduled. Each is labelled accordingly.

No certification claims. ReserveChain does not hold, and does not claim, ISO 27001, SOC 2 or any other security certification or attestation. No external penetration test or smart-contract security review has been completed yet. Both are planned before any activation. If a third party presents a ReserveChain security certificate, it is not genuine. Report it through the Anti-Fraud Notice.

Identity and access management

Six roles. No one approves their own work.

Access is role-based and least-privilege. Editing, approval, publication, compliance and system administration are separate permissions held by separate people. Publishing anything public requires a second person: the approver must differ from both the submitter and the last editor.

Application, sessions and portal

Implemented controls

Multi-factor authentication

Time-based one-time passwords (RFC 6238) with replay protection and single-use recovery codes, which are stored hashed. Shared secrets are encrypted at rest with AES-256-GCM.

[rc_status s="in_development"]

Sessions

Staff sessions expire after a working day. API access tokens last one hour. Refresh tokens are stored hashed and rotated on every use. If a refresh token is reused, every session for that account is revoked.

[rc_status s="in_development"]

Login protection

An account is locked after repeated failures, and failed sign-ins all show the same generic error. Author enumeration is blocked, and public forms and endpoints are rate-limited.

[rc_status s="in_development"]

Transport and headers

HTTPS with HSTS, a Content Security Policy, nosniff, frame restrictions and a strict referrer policy. Camera, microphone, geolocation, payment and USB permissions are disabled.

[rc_status s="in_development"]

Input and uploads

Uploads are limited to an allow-list of file types and a size ceiling, with a hook for malware scanning. Input is validated and output encoded. State-changing requests carry CSRF protection.

[rc_status s="in_development"]

Portal and module gating

Wallet, token-acquisition, holdings and redemption functions are built but locked at the server. Their endpoints report "inactive" whatever the client sends.

[rc_status s="not_applicable" label="Locked"]

Logging and monitoring

A tamper-evident record of every action

Sign-ins, failed sign-ins, role changes, workflow transitions, document uploads and replacements, module activations and recovery-code use are all written to an append-only, hash-chained audit trail. Database triggers block changes to it, and its head is anchored on-chain.

IP addresses are stored only as keyed hashes. This keeps the trail useful for investigation without turning it into a store of personal data.

Key management

No single key can move value

The smart contracts are designed for multisig administration from the start. Key custody arrangements for any live deployment are planned and not yet in place.

One administrator per contract, transferable only in two delayed steps[rc_status s="in_development"]Changing the administrator needs a begin step and an accept step separated by an enforced delay. This leaves time to detect and cancel a hostile transfer.
Narrow operational roles[rc_status s="in_development"]Minting, burning, pausing, KYC updates, reserve attestation and audit anchoring are separate roles and can be held by separate keys.
Multisig administrator[rc_status s="proposed"]The contracts are compatible with a multisig administrator. The signer set and threshold are subject to governance approval.
Hardware wallets for every signer[rc_status s="proposed"]Planned for all administrative and operational signers, with a documented key ceremony.
Application secrets[rc_status s="in_development"]Held in environment configuration, never in the repository. No credentials are shared, and accounts can be deactivated immediately.

Infrastructure, data, vendors, response

The rest of the programme

Infrastructure

  • Separate development, staging and production environments
  • Staging is never indexed
  • Encrypted automated backups with periodic restore tests
  • Release approval and rollback procedures
  • All accounts owned by ReserveChain, none by individual developers
[rc_status s="in_development"]

Data protection

  • Field-level visibility: public, participant, auditor, restricted
  • Confidential documents are served only to authorized roles
  • No personal data in analytics or URLs
  • No non-essential tracking before consent
  • Retention, correction and deletion procedures
[rc_status s="in_development"]

Incident response

  • Alerts on failed logins, security events, backup failures and deployments
  • Contract pause and account freeze as containment
  • Audit-chain verification to establish the timeline
  • Notifications on the official channels only
[rc_status s="proposed"]

Vendor controls and testing

  • An inventory of third-party services and dependencies
  • Dependency vulnerability review on each release
  • Contract unit tests, coverage and static analysis on every change
  • Independent penetration test and contract security review before activation
[rc_status s="proposed"]
