Stack

Deliberately conventional, verifiable by design

The stack uses established components so that the novel parts — evidence sealing, workflow binding and reserve-gated issuance — are small enough to inspect. This page describes the implementation that exists. It is in active development and has not yet had an external security review.

Registry and passport records

A declarative schema and a sealed passport

Each registry record type, from program and lot to container, bobbin, certificate, custody receipt and reserve report, is declared once in a schema. That schema defines the fields, units, visibility and the evidence each field must link to. The editor, the API and the passport are all generated from it, so they cannot drift apart.

Record fingerprint

For each passport, the platform computes a SHA-256 hash over the passport number, record type and every public field as key-value pairs. Changing any published value changes this fingerprint.

Document leaves

Every linked document has a SHA-256 hash, computed from the stored file when it is uploaded. These hashes and the record fingerprint form the leaves of the passport's Merkle tree.

Merkle root

The leaves are de-duplicated, sorted and hashed in pairs up to a single SHA-256 root. One 64-character value commits to the entire evidence set, and anyone holding the JSON export can recompute it.

Smart contracts

Six contracts. Every economic value unset.

The contracts are a proposed ledger layer. Price, supply, the asset-to-token ratio, redemption thresholds and allocations are configuration inputs, and all of them default to unset, zero or disabled. With the shipped configuration, minting and redemption are both blocked. Deployment tooling refuses mainnet targets.

ReserveToken

An ERC-20 token with EIP-2612 permit and pause. Minting succeeds in only two configured modes: within the reserve guard's limit, or within an explicitly enabled static cap. In every other state it reverts. Burning is restricted to a dedicated role.

ComplianceRegistry

Holds one record per address: approval status, a two-letter jurisdiction code, an expiry and a frozen flag. Transfers need both parties to be eligible. Blocked jurisdictions are a configurable set, and the deployment configuration seeds it with EU/EEA codes.

ReserveGuard

Attestors post the program, the units held, a report hash, a URI and an as-of date. The mintable amount is units × ratio − supply, and it falls to zero if the ratio or staleness window is unset or the attestation is stale.

RedemptionManager

The holder requests redemption and tokens move into escrow. An operator either approves, which burns the tokens and records a fulfilment reference, or rejects, which releases them back. The holder can cancel while the request is pending. The module is disabled by default and its thresholds are unset.

Treasury

A role-controlled holder of program tokens. It enforces a daily withdrawal limit per token, and an optional timelock queue delays large withdrawals. The default limit is zero.

AuditAnchor

Records the CMS audit trail's chain head, sequence number and URI. Sequence numbers must strictly increase. Anyone can call verify(seq, head) to confirm that a published head matches the on-chain anchor.

Audit logs

An audit trail that can be checked from outside

Audit logs are only useful if the operator cannot rewrite them. ReserveChain protects them with four independent layers.

The live status below is computed by walking the whole chain and recomputing every hash.

  1. Application

    The log has no edit or delete path in the admin, the API or the CLI. Rows can only be appended.

  2. Database

    MySQL BEFORE UPDATE and BEFORE DELETE triggers reject any attempt to change a row, even with direct database access.

  3. Cryptographic

    Each row commits to the previous row's SHA-256 hash. Editing, inserting or removing any entry breaks every hash after it.

  4. External

    The chain head is periodically anchored in AuditAnchor on a public test network, so silently rewriting history would also require rewriting the chain.

APIs and integration model

One API, every channel

The website, portal and the iOS and Android apps use the same versioned endpoints. Enterprise integrations would use them too. A figure on a passport page and the same figure in the app come from one query.

Public read

  • GET /rc/v1/programs — programs and their published fields
  • GET /rc/v1/passports/{no} — a full passport with Merkle root
  • GET /rc/v1/verify?hash= — match a fingerprint to a published document
  • GET /rc/v1/documents · /registry/stats · /audit/head

Authenticated

  • Sign-in issues a short-lived JWT access token and a rotating refresh token
  • TOTP second factor with single-use recovery codes
  • /me, holdings, transactions and notifications for participants
  • Value-moving endpoints respond "module inactive" until authorized

Scalability and roadmap

What scales, and what comes next

Scaling depends mainly on records and evidence, not on transactions. Token and redemption contracts are deployed per program, while compliance, reserve guard and anchoring are shared, so adding a program does not alter existing ones. Passports are computed from approved records and can be cached between publications. The audit chain grows linearly and is anchored in batches.
