Library principles

One source of truth for every document

Documents are published only after four-eyes approval. One person prepares the record, and a second, different authorised person approves it. Each release gets a version, an issue date, a status and a SHA-256 fingerprint. Superseded versions stay registered, so an older copy can still be identified and dated.

01

Versioned

Each release has a version identifier and an issue date. Any change, however small, produces a new version. A published file is never silently replaced.

02

Fingerprinted

A SHA-256 fingerprint is computed from the exact bytes of the file. If a single byte changes, the fingerprint changes completely.

03

Status-labelled

Each document shows whether it is a draft, a specimen, an owner-supplied copy or an approved release. The status describes the document, not the underlying arrangement.

04

Audit-logged

Every upload, approval and supersession is written to a hash-chained, append-only audit trail. Any later alteration of that history can be detected.

Version control

How a document enters the library

  1. Draft and register

    An editor uploads the file. The system computes its SHA-256 fingerprint at upload, and records the document type, version, issue date, issuer and the registry units it relates to.

    [rc_status s="in_development"]

  2. Independent approval

    A second authorised person, different from the editor, reviews the file against its source and approves or rejects it. Owner-supplied documents keep that label after approval.

    [rc_status s="in_development"]

  3. Publish and log

    Publication writes an entry to the hash-chained audit trail. Each entry includes the hash of the one before it, so the history cannot be rewritten without detection.

    [rc_status s="in_development"]

  4. Supersede, never overwrite

    A correction is published as a new version. The earlier version stays registered and marked as superseded, so anyone holding an older copy can identify it.

    [rc_status s="in_development"]

  5. Anchor on-chain

    The audit-trail head is intended to be anchored periodically to a public test network through the AuditAnchor contract. This gives the history an external timestamp.

    [rc_status s="proposed"]

Reading the documents

Three limits to keep in mind

A fingerprint proves integrity, not truth

A fingerprint match shows a file has not changed since registration. It does not show that the statements in the file are accurate. That depends on the issuer and on independent verification.

Owner-supplied is not independently verified

The two Certificates of Analysis were supplied by the asset owner. They have not yet been confirmed with the issuing laboratory or tested by an independent party appointed by ReserveChain.

No document here is an offering document

Nothing in this library is a prospectus or offering memorandum, and none of it is a solicitation. Any future definitive offering documentation would be separate. It would be shared only with eligible, approved persons.
