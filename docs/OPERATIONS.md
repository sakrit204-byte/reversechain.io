# ReserveChain.io — Operations: monitoring, alerts and on-call

> **Status:** Implemented for the single-server deployment (`deploy/`), subject to final approval of thresholds
> and contacts by ReserveChain. Related: [DEPLOYMENT-RUNBOOK.md](DEPLOYMENT-RUNBOOK.md) (deploy / rollback),
> [BACKUP-DR.md](BACKUP-DR.md) (backup / restore), [SECURITY.md](SECURITY.md) §10 (incident response).

Monitoring lives in the plugin module `wordpress/plugins/reservechain-core/includes/class-monitoring.php`
(`RC\Monitoring`, WP-CLI `wp rc-ops`). It has no external dependencies: checks run inside WordPress,
alerts go out by `wp_mail` (SMTP via `deploy/mu-plugins/rc-smtp.php`) and an optional webhook.

## 1. Health endpoints

### `GET /wp-json/rc/v1/health` (public, no secrets)

Rate-limited (60/min per client), `Cache-Control: no-store`, always HTTP 200 while WordPress and MySQL answer
(a dead database gives WordPress's own HTTP 500). Example:

```json
{"status":"ok","time":"2026-10-06T15:04:37+00:00","db":true,
 "audit":{"seq":982,"chain_head":"f0d7…","last_verify_ok":true,"last_verify_age_s":60},
 "triggers":true,"cron_age_s":11,"disk_free_pct":93.9,"backup_ok":true,
 "env":"staging","php":"8.3.35","wp":"7.1.2","rc":"0.9.0"}
```

`status` is `ok` or `degraded` (any check not OK). The chain head is already public (`/audit/head`).
`env`/`php`/`wp`/`rc` are only included when `RC_ENV` is not `production`.

### `GET /wp-json/rc/v1/health/full` (token-protected)

Send header `X-RC-Health-Token: <RC_HEALTH_TOKEN>` (from `~/reservechain/<env>/.env`; generated by deploy.sh,
at least 16 chars; an empty token disables the endpoint with 404, a wrong one gives 401). Returns every check with
detail, versions (PHP, WP, plugin, DB schema, MySQL), audit head + last verification + latest anchor, last
backup record, waitlist/contact/mail failures of the last 24 h, next WP-cron runs, alert state, site mode and
whether SMTP is configured.

```bash
curl -s -H "X-RC-Health-Token: $RC_HEALTH_TOKEN" https://reservechain.io/wp-json/rc/v1/health/full | jq .
```

On staging with basic auth, both endpoints stay reachable without the password (excluded in the Caddy block).

## 2. Checks and alerts

| Check | OK when | Alert (FAIL) when |
|---|---|---|
| `database` | `SELECT 1` succeeds | query fails |
| `audit_chain` | last full `Audit_Log::verify()` passed and is < 26 h old | verification failed (any error) — **SEV-2** (SECURITY §10) |
| `triggers` | both `rc_audit_no_update/delete` triggers exist (information_schema) | triggers missing |
| `failed_logins` | ≤ 20 `auth.login_failed` + `auth.api_login_failed` audit entries in the last hour | > 20 in the last hour |
| `submissions` | no waitlist/contact HTTP 5xx and no `wp_mail_failed` in 24 h (1–2 = warning) | ≥ 3 failures in 24 h |
| `backup` | last `wp rc-ops backup-mark` success < 26 h ago (n/a in development) | none recorded, last run failed, or older than 26 h |
| `disk` | ≤ 85 % used (filesystem holding `wp-content`) | > 85 % used |
| `cron` | WP-cron heartbeat < 20 min old (warning only) | — (visible on dashboard and `/health`) |

Schedules (WP-cron, driven by the real crontab every 5 minutes): heartbeat every 5 minutes; all checks
**hourly**; **full audit-chain verification daily at 03:15 UTC** (after the 02:30 backup) recorded in the audit
log as `ops.integrity_check`.

**Alert delivery:** e-mail to *ReserveChain → Settings → contact email* (falls back to the WordPress
`admin_email`), subject `[ReserveChain PRODUCTION] …`. Each failing check alerts at most every 6 h while it stays
failing and re-arms once it recovers. Every alert is recorded in the audit log (`ops.alert`).

**Webhook (optional):** Slack / Microsoft Teams / Mattermost incoming webhook, JSON `{"text": "…"}`:

```bash
wp option update rc_alert_webhook 'https://hooks.slack.com/services/T…/B…/…'   # https only
wp rc-ops test-alert                                                          # e-mail + webhook test
wp option update rc_alert_webhook ''                                          # disable
```

## 3. Admin dashboard widget "Operations"

WordPress Dashboard → **Operations** (users with `rc_view_audit` or `manage_options`): one row per check with
OK/WARN/FAIL and detail, the environment, and a **Run full checks now** button (verifies the whole chain and
sends alerts for failing checks).

## 4. WP-CLI

```bash
W="docker compose -p rc-production -f docker-compose.prod.yml --env-file .env run --rm wpcli wp"   # on the server
$W rc-ops health [--strict]      # detailed JSON (same as /health/full); --strict exits 1 unless ok
$W rc-ops check [--no-alerts]    # all checks incl. full chain verification
$W rc-ops backup-mark --file=<archive> --size=<bytes> --sha256=<hash> [--offsite]   # called by backup.sh
$W rc-ops backup-mark --failed --message='…'                                         # called by backup.sh on error
$W rc-ops test-alert
$W rc audit-verify ; $W rc tamper-test                                                 # existing plugin commands
```

Locally: `MSYS_NO_PATHCONV=1 docker compose run --rm wpcli wp rc-ops check --no-alerts`.

## 5. External uptime monitoring (recommended)

Internal checks cannot report that the whole server is down, so add one external monitor per environment:

* **UptimeRobot** (free: 50 monitors, 5-minute interval) or **Better Stack Uptime** (free: 10 monitors,
  3-minute interval, status page).
* Monitor type **Keyword** on `https://<SITE_HOST>/wp-json/rc/v1/health`, keyword `"status":"ok"`
  (alert when *not* present) — catches downtime, TLS/Caddy failures and degraded internal state. Add a plain
  HTTP(S) monitor on `/` for the public site, and enable SSL-expiry notifications.
* Alert contacts: the on-call e-mail plus the same Slack/Teams channel as `rc_alert_webhook`.
* Optional: Better Stack heartbeat for backups — append `&& curl -fsS https://uptime.betterstack.com/api/v1/heartbeat/<id>`
  to the backup crontab line so a *missing* backup run also pages.

## 7. On-call checklist

**Daily (5 minutes, or rely on alerts):** dashboard widget all green; last night's backup present
(`ls -l ~/reservechain-backups/production/daily | tail -2`); no unexplained `ops.alert` entries.

**When an alert arrives:**

1. Acknowledge in the channel; open `/health/full` (or `wp rc-ops health`) to see the exact failing check.
2. **Audit chain verification failure / triggers missing** → SEV-2. Do not "fix" data. Switch site mode to
   `maintenance` if tampering is suspected, preserve evidence (audit export, `mysqldump`), compare with the
   last on-chain anchor, follow SECURITY.md §10. Triggers missing without tampering: re-apply with
   `wp eval 'RC\Install::create_triggers();'` and run `wp rc tamper-test`.
3. **Excessive failed sign-ins** → check the `auth.login_failed` entries (hashed logins/IPs) for a pattern;
   confirm rate limiting works; block the source at the firewall/Cloudflare if sustained; ensure staff MFA.
4. **Waitlist/contact failures** → `wp rc-ops test-alert` to test mail; check SMTP credentials/quotas in `.env`,
   SPF/DKIM; `docker compose … logs wordpress` for PHP errors on `/wp-json/rc/v1/waitlist|contact`.
5. **Backup stale/failed** → read `logs/backup.log`; run `./backup.sh` manually; typical causes: disk full,
   passphrase/age key missing, rclone credentials expired. SEV-3, but fix the same day.
6. **Disk > 85 %** → `df -h`, `docker system df`; prune unused images (`docker image prune -a`), check
   `BACKUP_DIR` retention and `logs/`; grow the volume if needed.
7. **Site down (external monitor)** → `docker ps`; restart the stack
   (`docker compose -p rc-<env> … up -d`) and the edge (`docker compose -p rc-edge … up -d`); if a bad release,
   `./rollback.sh --to previous` (DEPLOYMENT-RUNBOOK §4.1).
8. Record what happened and the fix in the incident log; for SEV-1/2 follow the post-incident review.

**Weekly:** review `ops.*` and `auth.*` audit entries; confirm off-site copies exist (`rclone ls <remote>/production/daily`).
**Quarterly:** restore drill of a real production archive into staging (BACKUP-DR §9.3), record timings vs RTO.
**Secrets rotation:** `RC_HEALTH_TOKEN` and the backup key with staff changes; update the uptime monitor if the
token is used there (it is not needed for the public `/health`).
